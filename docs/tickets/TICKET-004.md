# TICKET-004 — Resolver reglas y propietarios Zoho reales

- **Estado:** DONE
- **Prioridad:** P0
- **Objetivo:** asignar cada servicio a un Owner real activo y verificable.
- **Contexto técnico:** v1 compara servicio exactamente con reglas DB y asesores demo. v2 usará Switch/Edit Fields y usuarios comprobados en TICKET-001.
- **Dependencias:** TICKET-001 y TICKET-003 DONE.
- **Alcance:** configurar RRHH/Legal/Automatización → ID Zoho real; verificar usuario activo/asignable; manejar servicio sin regla y usuario no disponible antes de guardar; permitir editar mapping sin IDs secretos en el frontend.
- **Fuera de alcance:** guardar lead, round-robin, IA, crear usuarios/licencias y mensajería directa.
- **Criterios de aceptación:** las reglas generan los IDs string verificados; servicio sin regla devuelve 422 sin guardar; ID desconocido/inactivo/no asignable o fallo de consulta devuelve error explícito sin Slack; nunca usar Owner implícito.
- **Casos de prueba:** comprobar las tres reglas, servicio `Otro`, ID inválido, usuario inactivo y consulta de usuarios sin permisos; cambiar mapping y verificar que la siguiente ejecución lo usa. Confirmar además que Zoho rechaza Owner inválido en TICKET-005.
- **Resultados esperados:** asignación determinística real y sin éxito falso.
- **Evidencia de pruebas (2026-10-23):** el usuario proporcionó IDs para RRHH (`6300195000001281004`), Automatización (`6300195000000468001`) y Legal (`6300195000001281013`); también confirmó que son activos/asignables, que hay credencial OAuth guardada en n8n y compartió el API base `https://www.zohoapis.com/crm/v8`. Esta confirmación inicial es reportada por el usuario. Después de que el usuario inició sesión, se configuró el host y se enlazó la credencial al nodo en n8n. Las pruebas HTTP de test mode consultaron `users?type=ActiveUsers` y devolvieron HTTP 200 con el Owner esperado para RRHH y Legal. Automatización dio HTTP 422 en el primer intento porque el cuerpo sintético local no preservó el carácter acentuado; repetido con JSON `\u00f3` UTF-8 devolvió HTTP 200 y el Owner esperado. `Otro` devolvió HTTP 422. Los tres Owner IDs coinciden con el mapping. El export estático mantiene 10 nodos, conexiones válidas, workflow inactivo y cero credenciales; la instancia n8n lo conserva inactivo y tiene una referencia de credencial configurada. `docker compose config --quiet`, validaciones estáticas de mapping, health HTTP 200 y `git diff --check` pasaron. El workflow no contiene nodos de escritura ni Slack, por lo que estas pruebas no guardaron Leads ni notificaron.
- **Evidencia adicional (2026-10-24):** en una copia temporal del workflow, se cambió RRHH a un ID sintético desconocido; una ejecución HTTP de test mode consultó la lista de usuarios activos y respondió HTTP 503 `owner_unavailable`. En otra copia temporal, se quitó la credencial solo del nodo de consulta para forzar un error local seguro; respondió HTTP 503 `owner_lookup_failed`. Estos casos no escribieron en Zoho ni notificaron. Las copias de prueba se eliminaron; la instancia conserva únicamente el workflow original inactivo. La segunda prueba verifica la ruta de error por credencial ausente, no un 403 real de Zoho.
- **Decisión de cierre:** por autorización explícita del usuario, se marca DONE con las limitaciones de prueba registradas: la prueba de Owner desconocido satisface el criterio alternativo de Owner no disponible; además, la ruta de fallo de consulta devuelve el error esperado. No se afirma que las pruebas NOT_RUN hayan pasado.
- **Notas de implementación:** el workflow normaliza `serviceRequested` mediante trim y comparación exacta, responde 422 para servicio sin regla, consulta `users?type=ActiveUsers` con OAuth y solo devuelve `Owner.id` string si está presente en la respuesta activa. El Owner desconocido y el fallo de lookup probado producen respuestas explícitas 503; no hay guardado, Owner implícito ni Slack en esta etapa. No conectar este endpoint directamente al frontend ni activar el workflow. Quedan NOT_RUN la prueba con un usuario Zoho realmente inactivo y la respuesta real de permisos insuficientes; no se modificó ni revocó la credencial existente. El rechazo por Zoho del Owner inválido al guardar corresponde a TICKET-005. TICKET-004 queda DONE por autorización del usuario, con dichas pruebas sin ejecutar claramente documentadas.
