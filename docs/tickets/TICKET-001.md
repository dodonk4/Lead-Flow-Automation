# TICKET-001 — Verificar Zoho, usuarios y contrato técnico

- **Estado:** DONE
- **Prioridad:** P0
- **Objetivo:** resolver requisitos externos y capacidades antes de diseñar el workflow de producción.
- **Contexto técnico:** Compose fija n8n 2.5.0. La documentación Zoho describe upsert de Leads, pero la cuenta, edición, campos, usuarios y soporte del nodo local no se han probado.
- **Dependencias:** ninguna. Requiere acceso autorizado del usuario a Zoho y una instancia/cuenta de prueba; usar entorno temporal aislado, sin modificar stack v1.
- **Alcance:** verificar región/DC, edición/API, OAuth, scopes efectivos, metadata/layout/obligatorios, límites y API names; comprobar usuarios activos/asignables y mapeo; ensayar upsert por Email, Owner y retorno de acción; confirmar capacidades del nodo n8n instalado. Documentar mapping y cualquier fallback.
- **Fuera de alcance:** workflow definitivo, cambios del frontend, retirar backend, crear usuarios o comprar licencias sin autorización.
- **Criterios de aceptación:** matriz real de campos obligatorios/API names/límites; mapping de servicios a IDs reales sin inventar valores; lectura de vuelta confirma Owner; segundo upsert con email igual devuelve el mismo Lead; acción create/update observable; decisión nativo vs HTTP autenticado documentada. Si falta cuenta/permisos/licencia, marcar BLOCKED.
- **Casos de prueba:** (1) OAuth permite leer metadata y usuarios; (2) Lead sintético nuevo con Owner válido devuelve ID y lectura confirma propietario; (3) repetir email actualiza mismo ID; (4) Owner inválido en prueba aislada falla sin éxito ficticio; (5) límites y obligatorios documentados.
- **Resultados esperados:** capacidad y contrato conocidos; ninguna credencial o ID inventado se versiona.
- **Evidencia de pruebas (2026-10-20):** rama `feat/zoho-crm`; sin dependencias previas. n8n aislado `leadflow-v2-n8n` (imagen `n8nio/n8n:2.5.0`, localhost `127.0.0.1:5678`, volumen `leadflow-v2-n8n-data`) respondió HTTP 200 en `/healthz`. El usuario informó que `fields` y `users` funcionaron; un primer upsert falló porque `activeOwnerId` conservaba el placeholder. Después, el usuario confirmó explícitamente que todos los casos del workflow pasaron de forma esperada. No se conservaron salidas detalladas, campos, mapping ni IDs, por petición del usuario; resultado registrado como confirmación del usuario, no reproducido independientemente. Inspección estática del paquete local: nodo Zoho CRM ofrece `Get Fields` y `Create or Update` para Leads; Email puede enviarse como campo adicional, pero las propiedades de Lead no exponen Owner ni `duplicate_check_fields`, y el ejecutor devuelve solo `data[0].details`, sin conservar `action`. Definición local de credencial declara scopes por defecto amplios (`ZohoCRM.modules.ALL`, `ZohoCRM.settings.all`); scopes efectivos no comprobados. Se preparó `n8n/leadflow-zoho-qualification.workflow.json`; el JSON se validó localmente con 8 nodos, inactivo, IDs únicos, conexiones existentes y cero credenciales embebidas.
- **Notas de implementación:** HTTP Request autenticado con `zohoOAuth2Api` es el fallback candidato para Owner y duplicate check explícito. TICKET-001 se cierra por confirmación del usuario de que todos los casos pasaron; el usuario acepta que no se retenga el detalle de metadata, mapping ni IDs. Esta omisión limita la reproducibilidad futura y no debe interpretarse como que esos valores quedaron documentados. No incluir tokens ni listas completas de usuarios. No iniciar automáticamente TICKET-002.
